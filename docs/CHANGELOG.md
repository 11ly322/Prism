## v8.4.3  （解码后 reduce 压图：滑杆回到 75ms）

- **Loader 里补一次 Image.reduce(k)**：libjpeg 不保证按请求给档位（请求 1904x1186
  仍可能解出 4000x2500），所以在解码后按画布尺寸做整数倍 reduce，并**同步
  doc.size 与 doc.draft_ratio**（后者关系到缩放/坐标换算，是这轮的主要风险点）。
  reduce 是逐格平均，比 LANCZOS 便宜得多，且发生在后台线程。
- **按 profile 分档**（2 核实测、3 轮）：
  | 档位 | 首帧 | 滑杆 |
  | :--- | ---: | ---: |
  | fast-first（两段式 + 保留大图）| **346 ms** | 181 ms |
  | **fast-slider（默认，解码后 reduce）** | 632 ms | **75 ms** |
  两者都 < 1 秒首帧。默认 fast-slider 把滑杆从 181 拉回 **75 ms**（此前目标 77 ms）。
- **paste 策略纳入 profile**：`--perf-profile fast-slider-paste` / `fast-first-new`
  可强制 PhotoImage 更新方式；不加后缀时按核数自动（<=4 核 paste）。
- **bench 修复**：`--perf-profile` 之前没有转发给子进程，导致 A/B 两组测的是同一份
  配置（数字完全一致才暴露出来）。现已转发。

## v8.4.2  （paste 分支 + perf-profile + 档位真相）

- **PhotoImage 按核数选择更新方式**：<=4 核走「复用 + paste」，多核仍每帧新建。
  微基准（1764x1396、2 核）：paste 28.6 ms vs 新建 59.6 ms（快 2 倍）；
  但整机 bench 里两者只差 6 ms（178 vs 184），说明拖动帧的大头不在这一步。
- **新增 --perf-profile fast-first / fast-slider / auto**，实测（真实 40MP、3 轮）：
  | 档位 | 首帧 | 滑杆 |
  | :--- | ---: | ---: |
  | auto（两段式 + 高档最终解码）| 314 ms | 184 ms |
  | **fast-slider（单段 + 低档）** | **341 ms** | **115 ms** |
  **默认改为 fast-slider**：首帧只慢 27 ms，滑杆快 69 ms。
- **查清「滑杆回不到 77ms」的真因**：请求 draft(1904x1186) 时 libjpeg 仍返回
  4000x2500（1/2 档），不是预期的 1/4 档；最终解码大 4 倍像素，滑杆自然慢。
  下一步应改成「解码后按画布尺寸 Image.reduce(k)」而不是继续调 draft 请求。
- 新增 PRISM_DEBUG_DECODE=1 环境变量，可把每次解码的 draft_to 与解出尺寸写进日志。

## v8.4.1  （退出噪音 + 两段式调参 + 拖动路径实测）

- **修退出期 after 任务未取消**：destroy() 的取消清单补上 _ai_job / _watch_job /
  grid_job / thumbs_job 等（之前漏了，退出时刷 invalid command name
  "..._refresh_ai_status"）；_refresh_ai_status 与 _watch_plugins 回调开头
  也加了 alive 检查。实测「开→关」全过程 **无错误输出**。
- **两段式条件改成「与图大小有关、与画布无关」**：实测（真实 40MP、2 核、3 轮）
  - 单段 + 低档最终解码：首帧 585ms、滑杆 77ms
  - 两段式 + 高档最终解码：首帧 327ms、滑杆 118ms
  - **两段式 + 低档**：首帧 **313ms**、滑杆 111ms  ← 当前采用
  首帧从 585 降到 313（-47%），滑杆从 77 升到 111（+44%）。
  这是取舍：首帧是承诺指标，滑杆 111ms 仍有约 9fps。
- **拖动帧 55ms 的成因已定位**：2 核下「复用 PhotoImage + paste」只要 28.6ms，
  而「每帧新建 + itemconfigure」要 59.6ms —— **paste 快 2 倍**。
  但 16 线程时结论相反（52.1ms vs 25.8ms），所以没有直接改，
  需要按 CPU 核数选择策略，留到下一轮做。
- **bench 新增 --slack**：可对比不同 DRAFT_SLACK 下的首帧/滑杆（本轮就是用它对出来的）。

## v8.4.0  （拖动帧拆解 + 长尾提示 + 常数化）

- **DRAFT_SLACK / SLOW_DECODE_MS 常数化**：draft 的 15% 余量、以及「解码超过多久算慢」
  都提到模块顶部，方便按机器调（实测 0.85 让 1764 画布落到 1/4 档）。
- **长尾提示**：Loader 记录每次解码耗时到 doc.slow_ms，超过 SLOW_DECODE_MS(2s) 时
  主线程 flash「这张图解码用了 X 秒（文件较大或磁盘较慢）」，避免用户以为卡死。
- **2 核拖动帧再拆一层**（真实 40MP）：
  整帧 77.6 ms = 调色 7.5 ms + PhotoImage 上传 ~15 ms + 其余 ~55 ms。
  瓦片缓存命中后 crop/resize 不再每帧执行，所以剩余时间在 surface 转换与
  Tk itemconfigure 上，**不在调色、也不在缩放**。
  结论：拖动路径没有值得动的单点，不做「拖动用代理图」。
- **2 核单段首帧复测：557 ms**（此前只有 16 线程的 425 ms 数据），仍 < 1 秒。

## v8.3.9  （性能：拖动帧拆解 + 去掉预览跳变 + 承诺恢复）

- **2 核拖动帧拆解（数据先行，结论与预期相反）**：整帧 68 ms，其中调色 6 ms、
  PhotoImage 上传 15 ms、美颜 0 ms（没开）、代理图 0 ms。
  **拖动不需要代理图** —— 瓶颈不在调色，改代理图渲染没有收益，因此不实施。
- **预览跳变处理**：两段式会让用户先看到 2000x1250、300~700ms 后跳到 4000x2500。
  实测 draft(900)/draft(1100)/draft(1400) 解出来**都是 2000x1250**（libjpeg 档位相同），
  所以「提高预览尺寸」没有任何收益。真正的浪费是：画布 1764x1396 因高度差 146px
  退回 4000x2500 那一档，多解 4 倍像素。
  处理：draft 请求统一留 15% 余量；两段式只在大画布（>2000）时启用。
  典型笔记本画布下变成**单段解码 425 ms、无跳变**（两段式是 223 ms 但有跳变）。
- **README 首帧承诺改回「< 1 秒」**，这次附数据：两段式 223 ms（标准差 2 ms）、
  单段 425 ms，均来自真实 18MB / 4000 万像素图，不再引用纯色测试图。

## v8.3.8  （性能：两段式加载，压首帧长尾）

- **大图（>8MB）两段式加载**：Loader 先按 900 长边解一张预览并立刻推给主线程，
  再按正常 draft 解一次并替换。预览不生成代理图，省掉一次缩放。
  实测（真实 18MB / 40MP）：**237ms 出预览（2000x1250）→ 首帧可见 292ms**，
  773ms 补齐 4000x2500 全质量。改动前同口径首帧 585~602ms，
  且完整解码期间用户看到的是空白。最大收益不是中位数，而是**长尾**：
  完整解码再慢，用户 300ms 内也能看到图。
- **两条被数据否掉的思路（未实施，避免反复试错）**：
  1. 按短边请求 draft 争取 1/4 档：只快 15ms（4%），PSNR 掉到 40.3 dB。
     原因：JPEG 的 DCT 缩放省的是输出缓冲，熵解码仍要跑完整帧。
  2. 用 reduce 在画布尺寸上二次降采样：两步 326ms vs 单步 228ms。
     原因：4000->1764 的整数倍只有 1（高度 1.79），reduce 不触发。
- 修 _wanted 的 3 元组解包（两段式引入预览项后变成 4 元组）。

  fit 视图肉眼看不出差别，放大查看另走全分辨率解码。
  实测（真实 18MB 图、3 轮）：首帧中位 **602 / 585 / 8744 ms**（第三轮撞上系统卡顿），
  前两轮 590~600ms；改动前同口径是 2400ms。
- **撤回不成立的假设**：曾怀疑缩略图线程与首帧抢资源，实测开 624/1103ms、
  关 1071/1128ms —— 无相关性，未做任何「暂停缩略图」的改动。
- **README 更正承诺口径**：不再单方面写「首帧 < 1 秒」，改成
  「16 线程中位 590ms，冷缓存或系统繁忙时可到 2.5s」，并注明该数字来自
  真实 18MB 图而非纯色测试图。
- **bench 测试图**已在上版换成真实感大图；本版在 README 说明原因。

## v8.3.6  （性能：启动与解码，未发版）

1) **面板非首屏分区推迟构建**（成功）
   _build_panel 只同步建「基本 / 镜头 / 高级」，其余 8 个分区用 after(1) 逐个构建，
   并用一个 holder 容器占位保证 UI 顺序不变。
   首帧可见：16 线程 1411 -> 1253 ms（-11%），2 核 1272 -> 1034 ms（-19%）。

2) **首帧缩放改两步降采样**（失败，已回退并写注释）
   4000x2500 -> 1764x1396 时整数倍只有 1（高度 1.79 倍），reduce 不触发，
   实测两步 326 ms、单步 228 ms。reduce 的收益要 >=4 倍才出现。

3) **非 RAW 从路径解码，不再常驻整个文件**（成功）
   原先 read() 全文件 + BytesIO 解码，一张 30MB 的 40MP JPEG 等于多占 30MB、
   多一次整块拷贝；doc.data 只被内存估算用到。改为 Image.open(path)，
   记录 file_bytes 供估算，load 后关闭句柄。
   实测（30.3MB 真实 40MP，2 核限流）：解码 325 -> 310 ms，常驻内存 -30MB。

4) **真实图端到端**：2 核限流下打开 30.3MB / 40MP JPEG，首帧 **698 ms**（< 1 秒）。

5) 顺带修 newcheck 三条过时断言（插件数 5 -> >=9、全屏已移除 -> 兼容模式、
   F11 无绑定 -> 已绑定），现在 29 项全过。

**测量口径问题（重要）**：bench 用的 40MP 测试图是纯色，只有 0.6MB，解码仅 30ms，
导致解码优化在 bench 里完全体现不出来；上面第 3、4 条的数字是用带噪声的
30.3MB 真实感测试图单独测的。下一轮应把 bench 默认图换成真实感大图。

  **两点如实说明**：① 输入的值会**吸附到该滑块的步长**（曝光步长 0.05，输入 1.37 实际得到

  极限**（窗口传的是 -5~5，但曝光滑轨本身是 -3~3，输入 99 得到 3.0）。

- 附带结论（**启动优化到此为止**）：又剖析了一轮启动，构造 198 ms 里 **155 ms 是
  `_tkinter.create`**（Tk 解释器+窗口创建），Python 侧只剩 43 ms；首次 `update()` 256 ms
  也基本是 Tk 自己的布局与映射。**没有可捡的余量了**，再去「优化」只能是自欺欺人。
